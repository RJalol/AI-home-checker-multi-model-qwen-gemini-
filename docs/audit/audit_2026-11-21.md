## 2. Topilmalar

Daraja: **O'rta** = production'dan oldin tuzatish; **Past** = rejaga kiriting; **Ma'lumot** = bilib qo'yish.
"Tasdiqlandi" = kod o'qildi yoki haqiqiy stekda sinab ko'rildi.

### O'rta

**F1. Juda uzun maydonlar HTTP 500 beradi.** Tasdiqlandi (sinov): `student_name` 300 belgi, `skill_key` 100 belgi, `external_submission_id` 300 belgi, uchalasida ham 500. DB ustunlari `String(255/32)`, API esa uzunlikni tekshirmaydi. *Tuzatish:* barcha matn maydonlari uchun uzunlik tekshiruvi, 422 qaytarish.

**F2. `extra_instructions` cheksiz.** Tasdiqlandi (sinov): 500 KB qabul qilindi. U har baholash promptiga kiradi, ya'ni xato yoki suiiste'mol token xarajatini va kechikishni oshiradi, kesh kalitiga ham tushadi. *Tuzatish:* 2–4 ming belgi chegarasi (task_text/answer_key uchun 20 000 chegara allaqachon bor).

**F3. Yuklangan fayl to'liq xotiraga o'qiladi, hajm tekshiruvi keyin.** Kod o'qildi: `file.file.read()` so'ng `validate_upload` (25 MB). Ilova darajasida so'rov hajmi chegarasi yo'q. Pillow rasm o'lchamini faqat standart himoya bilan cheklaydi (≈178 mln piksel ≈ 0.5 GB). Yuk ostida sinalmagan. *Tuzatish:* reverse proxy'da `client_max_body_size`, bo'laklab o'qish, `Image.MAX_IMAGE_PIXELS` ni aniq (masalan 50 mln) qo'yish.

**F4. Fayllarni saqlash muddati yo'q va "yetim" fayllar.** Kod o'qildi: o'quvchi fotolari (voyaga yetmaganlar) diskda abadiy qoladi, o'chirish funksiyasi yo'q. Fayl bazaga yozishdan oldin saqlanadi, shuning uchun CRM qayta yuborganda (bir xil `external_submission_id`) har safar yangi fayl yoziladi, mavjud topshiriq qaytadi. *Tuzatish:* tasdiqlangandan N kun keyin o'chiradigan vazifa; faylni faqat yangi topshiriq yaratilganda saqlash; `training_data/` uchun ham muddat.

**F5. Webhook imzosi zaif sozlanishi mumkin.** Kod o'qildi: (a) master sir bo'sh bo'lsa webhook imzosiz yuboriladi (jim, xatosiz); (b) sir `WEBHOOK_SIGNING_SECRET` bo'lmasa `INTERNAL_API_KEY` dan olinadi, ya'ni admin kalitini almashtirish hamma tashkilotlarning webhook sirini jimgina o'zgartiradi va CRM tekshiruvini buzadi, admin kaliti oqsa barcha webhooklarni soxtalashtirish mumkin. *Tuzatish:* production'da `WEBHOOK_SIGNING_SECRET` ni majburiy qilish (startupda xato), uni admin kalitidan ajratish.

**F6. Tashkilot (org) bo'yicha kvota/rate limit yo'q.** Kod qidirildi: API darajasida cheklov yo'q (faqat provayder darajasida `HWCHECKER_RATE_LIMIT_PER_MINUTE`). Oqib ketgan org kaliti yoki CRM'dagi cheksiz qayta urinish halqasi (har safar yangi `external_submission_id`) cheksiz pullik chaqiruv yaratadi. Byudjet kuzatuvchisi faqat ogohlantiradi. *Tuzatish:* org bo'yicha kunlik topshiriq chegarasini yuqori (haqiqiy yuklamadan ancha baland) qo'yish, bu sifatga ta'sir qilmaydi, faqat himoya; org bo'yicha xarajat ogohlantirishi.

**F7. CI, Docker va pinlangan bog'liqliklar yo'q.** Kod o'qildi: `requirements.txt` da faqat `>=`, lock fayl yo'q, `pytest` ro'yxatda yo'q, `.github/` yo'q, Dockerfile yo'q. Natija: build takrorlanmaydi, bugungi 207 test o'tishi ertaga yangi kutubxona versiyasida kafolatlanmaydi. *Tuzatish:* lock fayl (`pip-tools`/`uv`), Dockerfile, GitHub Actions (testlar + bandit + pip-audit).

### Past

**F8. Provayder xatosi matni foydalanuvchiga ko'rinadi.** Kod o'qildi: baholash muvaffaqiyatsiz bo'lsa `reviewer_note = "Grading failed: " + str(exc)` saqlanadi va CRM/o'qituvchiga qaytadi. Provayder xato matnida ichki ma'lumot (URL, so'rov ID) bo'lishi mumkin; aniq tarkibi tekshirilmagan. *Tuzatish:* mijozga umumiy xabar, tafsilot faqat logga.

**F9. Qayta baholashga umr bo'yi chegara yo'q.** Sinov (taxminim qisman noto'g'ri chiqdi): bir vaqtda takrorlash 409 bilan bloklanadi (200, 409, 409), lekin har bir tsikl keshni chetlab o'tib to'liq pul sarflaydi. *Tuzatish:* topshiriq bo'yicha hisoblagich (masalan ≤ 3).

**F10. Legacy yo'l byudjet kuzatuvchisidan tashqarida.** Tasdiqlandi: `record_spend` faqat `grading_router` ichida. Eski dvigatel (Speaking va boshqa fanlar) xarajati kunlik/oylik ogohlantirishga kirmaydi, cross-vendor tekshiruv ham yo'q.

**F11. DNS rebinding (webhook).** Hujjatlashtirilgan qoldiq xavf: DNS tekshiruvi va ulanish orasida manzil almashishi mumkin. Redirectlar o'chirilgan (`allow_redirects=False`), bu yaxshi. *Tuzatish:* worker hostida ichki diapazonlarga chiquvchi trafikni firewall bilan yopish.

**F12. Natija keshi tashkilotlar orasida umumiy.** Kod o'qildi: kalit fayl baytlari + prompt + sozlamadan, org ID kiritilmagan. Bir xil fayl ikki tashkilotda bir xil natija oladi. Ma'lumot oqishi minimal (faqat o'sha fayl bahosi), lekin boshqa tashkilot shu faylni yuborgani vaqt bo'yicha sezilishi mumkin. Kalitga org ID qo'shish xarajatni oshiradi (kam moslik), shuning uchun qaror biznesga bog'liq.

**F13. Standart DB parol (`postgres:postgres`).** `DATABASE_URL` berilmasa shu qiymat ishlatiladi. Production'da xato bilan ishga tushish xavfi. *Tuzatish:* production rejimida majburiy env.

### Ma'lumot / dizayn taxminlari

**I1. Tashkilot ichida o'qituvchi shaxsi tekshirilmaydi.** Org kaliti egasi tashkilotning har qanday topshirig'ini tasdiqlay/tahrirlay oladi; `teacher_external_id` ni CRM beradi. CRM o'qituvchi-o'quvchi ruxsatlarini o'zi nazorat qilishi shart.

**I2. O'quvchi ma'lumotlari tashqi provayderlarga ketadi.** Ishlar (voyaga yetmagan o'quvchilar fotolari) Alibaba (Qwen), Z.ai (GLM), Google, Anthropic va OpenAI'ga yuboriladi. Maktab/ota-onalar roziligi, provayder shartlari (ma'lumotni o'qitishda ishlatmaslik) va O'zbekiston shaxsiy ma'lumotlar qonunchiligiga muvofiqlik tekshirilishi kerak. Men yurist emasman, bu tekshiruvni mutaxassis bilan o'tkazing. Prompt'ga o'quvchi ismi kirmaydi (kodda tasdiqlandi), lekin o'quvchi o'z ismini ish ichiga yozishi mumkin.

**I3. Haqiqiy provayderlar bilan sinalmagan.** Hamma testlar soxta SDK bilan. Model nomlari, thinking parametrlari (`thinking_level`, `enable_thinking`, `reasoning_effort`, `output_config.effort`) va keshlangan token maydonlari rasmiy hujjatlarga qarab yozilgan, lekin jonli chaqiruvda tasdiqlanmagan. Provayder o'zgartirsa, kod "tashlab, ogohlantirib, qayta urinadi", ya'ni baholash to'xtamaydi, lekin tejash yoki sifat jimgina yo'qolishi mumkin. Bu eng katta funksional noaniqlik.

**I4. Qamrov bo'shliqlari.** Past qamrov: `report_generator` 30%, `token_usage_logger` 13%, `batch_processor` 18%, `cache_registry` 22%, `benchmarks/compare_candidates` 31%; 0%: `worker_entrypoint`, `self_hosted`, `app.py`, `local/cloud/anthropic_checker` (~520 operator). Yangi pipeline'ning asosiy qismlari (router, providerlar, budget, review, webhook) 77–95% qamrovda.

**I5. Ikki dvigatel birga.** Eski bitta chaqiruvli dvigatel va yangi `hwchecker/` yo'li bir kodda: ikki xil narx modeli, ikki xil test darajasi, ko'proq ta'mirlash. Yangi mahsulot uchun eski qismni bosqichma-bosqich olib tashlash rejasi kerak (avval Speaking/audio'ni `hwchecker` audio tier'iga o'tkazish).

**I6. Prompt-injection himoyasi bor, lekin sinalmagan.** `UNTRUSTED_INPUT_BLOCK` ishlatiladi; o'quvchi ishiga "100 ball qo'y" kabi ko'rsatma yozilsa nima bo'lishi o'lchanmagan. O'qituvchi tasdig'i asosiy himoya.

## 3. Kuchli tomonlar (saqlab qoling)

- Admin kaliti: doimiy vaqtli taqqoslash, kalit yo'q bo'lsa 503 (yopiq holda ishlaydi).
- Org kalitlari: 256-bit tasodifiy, bazada faqat SHA-256 xesh (bunday yuqori entropiyali kalit uchun yetarli); har so'rov `organization_id` bo'yicha cheklangan (tenantlar orasida IDOR yo'q, testlar bor).
- Webhook: HTTPS majburiy, SSRF tekshiruvi (yuborishdan oldin qayta), redirect yo'q, HMAC-SHA256 + vaqt belgisi.
- Fayllar: UUID nomi (yo'l manipulyatsiyasi yo'q), kengaytma va mazmun mosligi, rasmni dekodlash orqali tekshirish, hajm cheklovi.
- Hisobot HTML: `nh3` tozalash, qat'iy CSP.
- Ishonchlilik: idempotent topshirish, `reconcile` bilan qolib ketgan ishlarni qayta navbatga qo'yish, circuit breaker, qayta urinish, deadline.
- Xarajat: boshqa provayderdan ikkinchi fikr, byudjet ogohlantirishi, model almashganda keshni yangilash, `tokens.cached` o'lchovi.
